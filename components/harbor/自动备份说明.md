# Harbor一键暂停、备份、恢复（2.0）

## 更新

上传harbor-ops-auto-2.0.zip到ops253的/home/ops，确认没有正在执行的Harbor备份，再更新Python程序；不覆盖已有JSON、SSH或API凭证：

```bash
cp -a /opt/harbor-backup /opt/harbor-backup.before-auto
unzip -o /home/ops/harbor-ops-auto-2.0.zip '*.py' -d /opt/harbor-backup
```

使用现有/etc/core-backup-ops/harbor248.json，以及248本机/root/.harbor-backup.netrc。无需再次设置NAS挂载或复制管理员密码。

## 一键执行

```bash
nohup python3 -u /opt/harbor-backup/harbor-backup.py >> /var/log/harbor-backup.log 2>&1 < /dev/null &
tail -F /var/log/harbor-backup.log
```

无需先手动勾选只读，无需--writers-quiesced。--check只读检查，原本不是只读也可通过；不更改状态。

## 自动流程

1. 检查NAS三端真实挂载、容量、写读删、源目录、数据库及API。
2. 读取原只读状态、任务队列暂停状态及只读记录调度器状态，保存维护状态文件。
3. 开启仓库只读，阻止新推送/删除；暂停全部已登记的后台执行队列（不修改调度器状态），等待已有worker任务结束，默认最多5分钟。不强杀、不清空队列、不停止数据库/拉取服务。
4. 等30秒让在途请求收敛，重新检查只读与队列状态，然后流式备份数据库、镜像及配置到NAS243。
5. 收集完成后立即恢复原状态并回读确认，再从NAS243复制到NAS240/Windows254。原本已只读则仍保持只读，不擅自开放；原本整体暂停的队列仍保持暂停。
6. 一般异常及SIGTERM/SIGINT会在finally中尝试恢复。恢复失败产生CRITICAL告警，维护状态文件保持active，禁止新备份覆盖现场。

若现有队列部分暂停，脚本拒绝修改，避免覆盖管理员配置。API返回结构不认识也拒绝继续。只读与队列暂停不能提供与存储快照完全相同的原子性；拉取统计、登录会话等非核心状态不承诺完整恢复。镜像未完成_uploads排除。

部署前核对实际Harbor2.13.1 API行为。此版本通过本地模拟测试，未在你的生产Harbor执行自动暂停/恢复。首次在可观察窗口运行，确认推送恢复、拉取可用，再考虑每周日03:00自动任务。

## 故障恢复

正常脚本异常会尝试恢复，但kill -9、ops掉电、248失联不可能依赖finally保证成功。维护状态记录：

```text
/var/lib/core-backup-ops/harbor248/maintenance-state.json
```

连接恢复后，ops执行以下命令只恢复原设置，不生成/删除备份：

```bash
python3 -u /opt/harbor-backup/harbor-backup.py --restore-only
```

必须看到ORIGINAL_WRITE_AND_QUEUE_STATE_RESTORED，并确认网页实际状态。不删除状态文件绕过检查；不在维护active时更换host/API凭证对应的Harbor实例。

## 仍然独立的事项

此包暂不自动清理Harbor最近3份之外的历史，未接入GitLab网页。当前校验为大小检查，不是MD5；复制完成不代表已演练恢复。原先首份备份文档中的手动只读操作已被本自动流程替代。

调度器状态只读取、不修改。计划任务可能继续排队，已登记队列暂停期间不开始执行。备份开始与结束会复核所有队列暂停状态；出现新未暂停队列会阻断发布。依据Harbor2.13.1官方API与源码核对，不使用stop/清空队列动作。
