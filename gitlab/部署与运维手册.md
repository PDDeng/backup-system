# 核心资产备份平台部署与运维手册

版本：平台包 2.0；基于模块化分发 1.4。适用日期：2026-11-19。

## 1. 当前实际能力与边界

已实现：GitLab 客户端本地生成，中台 SSH 收集，挂载 SMB 分发，MD5 开关，按成功日期保留，Webhook，历史 MD5 周任务，网页连接检查、容量和最近结果展示。

本手册不把“上传完成”视为“已验证可恢复”。速度模式只检查文件存在、大小和归属凭据，同大小损坏仍可能漏检。恢复演练尚需在隔离环境完成。

|组件|当前生成方式|中台适配状态|
|---|---|---|
|GitLab 六台|客户端 gitlab-backup.sh|可执行检查、收集、分发、清理及历史校验|
|Oracle 41/46|独立 Windows Data Pump 脚本；另有 NAS 直写试验包|未接入网页执行和通用收集协议；41 的 rc=5 导出不能记成功|
|SVN29|计划 svnadmin hotcopy 到可用 NAS|目前 SMB 连接未验收，不得把原始在线目录复制当成功备份|
|Nexus|需确认真实 10.10.10.51 的系统和工作目录|未实现一致性备份适配；10.10.11.51 不是已确认 Nexus 主机|
|Harbor|计划周日03:00，暂停写入，保留拉取|尚未实现备份及恢复原只读状态适配器|

**不要把 Oracle/SVN/Nexus/Harbor 配置直接命名成 opsNNN.json 塞进当前 GitLab 调度器。它会按 GitLab 协议处理。**

## 2. 结构、通信与文件位置

```text
客户端 cron -> 官方 GitLab 备份命令 -> 本地归档+配置包+完成标记
                                       |
                      ops 以 SSH 公钥认证只读获取
                                       v
ops 中转目录 -> SMB 挂载 -> NAS243 / NAS240 / Windows254
     |                      每端独立结果与保留策略
     +-> 日志、结果 JSON、Webhook HTTPS443

Windows 管理电脑 -> SSH隧道 -> ops 127.0.0.1:8088 网页
```

- ops：10.10.10.253、192.168.1.212；旧211不再使用。
- 客户端 SSH：TCP22；ops 必须有到所有源端的路由。
- SMB：TCP445；客户端生成不需要直接访问 NAS，当前 GitLab 由 ops 访问。
- Webhook：由执行通知的主机访问 HTTPS443，需要 DNS/TLS 和出口可用。
- NTP：UDP123，与备份通信分开；时间统一 Asia/Shanghai。

|位置|用途|
|---|---|
|客户端 /opt/core-backup/gitlab-backup.sh|源端生成脚本|
|客户端 /etc/core-backup/gitlab.conf|部署模式、容器名、源备份目录、容量门槛|
|客户端 /var/log/core-backup/gitlab.log|源端完整日志|
|源备份目录/.core-complete/运行号/DONE|完成标记；缺标记不擅自认定归档成功|
|ops /opt/core-backup-modular|新版执行程序及网页|
|ops /etc/core-backup-ops/ops编号.json|每台 GitLab 配置|
|ops /etc/core-backup-modular/settings.json|可选全局配置|
|ops /etc/core-backup-ops/notify.json|中台告警配置，权限600|
|ops /opt/core-backup-ops/ssh|私钥、known_hosts，目录700私钥600|
|ops /var/lib/core-backup-ops/gitlab编号|中转、回执、最后结果、删除审计|

**中转空间**：先收集到ops，所有配置目标成功后删除该次已知中转文件；失败时保留。不要递归清空正在运行的staging。

## 4. 从零部署：先客户端，再 ops

### 4.1 准备客户端安装包

平台包内 client/ 包含现有已用的 gitlab-backup.sh、notify.py、配置样例与 install-client.sh。不要把 ops 的 Python3 模块复制到旧 CentOS 作为客户端执行。

上传 client/ 内容到目标 /root/core-backup-upload。编辑该机器配置，例如：

```bash
ASSET='gitlab07_10.10.10.200_新增代码库'
DEPLOY='docker'
CONTAINER='gitlab'
MODERN='no'
BACKUP_DIR='/data/gitlab/backups'
MIN_FREE_GB=25
```

MODERN=yes 用于现代 gitlab-backup create；旧10.x使用 no。BACKUP_DIR 必须是真实宿主机归档路径，与 GitLab 运行配置一致，不能仅修改这里把归档迁移。

安装前读脚本，使用统一安装器：

```bash
bash /root/core-backup-upload/install-client.sh /root/core-backup-upload/gitlab-new.conf
```

如需逐项可审计安装，执行以下明确命令，不依赖安装器参数：

```bash
mkdir -p /opt/core-backup /etc/core-backup
install -m 700 /root/core-backup-upload/gitlab-backup.sh /opt/core-backup/
install -m 600 /root/core-backup-upload/notify.py /opt/core-backup/
install -m 600 /root/core-backup-upload/gitlab-new.conf /etc/core-backup/gitlab.conf
install -m 600 /root/core-backup-upload/notify.json /etc/core-backup/
bash -n /opt/core-backup/gitlab-backup.sh
cat /etc/core-backup/gitlab.conf
df -h /实际备份目录
df -i /实际备份目录
```

notify.json 使用自己的 Webhook，不在文档和分享包里放真实密钥。原文件已存在时先备份，避免覆盖生产凭证。

### 4.2 首次本地生成与验收

确认没有已有备份进程，空间和 inode 充足，再手动运行一次：

```bash
/bin/bash /opt/core-backup/gitlab-backup.sh /etc/core-backup/gitlab.conf
tail -n 60 /var/log/core-backup/gitlab.log
```

必须看到 SOURCE_COMPLETE、END rc=0，且 DONE、files.tsv 指向实际存在的归档、gitlab-config.tar.gz、version-manifest.txt。只看到 tar 文件不够。

### 4.3 客户端定时任务

先保存旧任务，然后 crontab -e。不要覆盖其他业务任务。

```bash
crontab -l > /root/crontab-before-core-backup.txt 2>/dev/null
crontab -e
```

14用00:00，其余当前五台用01:00：

```cron
0 1 * * * /bin/bash /opt/core-backup/gitlab-backup.sh /etc/core-backup/gitlab.conf >> /var/log/core-backup-cron.log 2>&1
```

注释旧 GitLab 生成、chmod777、rsync、clean3.sh 等已被替代项。不要禁用不明数据库归档清理任务。验证 date -Is、crontab -l、systemctl is-active crond。Ubuntu 的服务名是 cron。

### 4.4 ops 依赖与解压

本版无需 Docker；使用 Ubuntu24.04自带 Python3：

```bash
apt-get update
apt-get install -y python3 openssh-client cifs-utils util-linux unzip
mkdir -p /opt/core-backup-modular /etc/core-backup-ops /etc/core-backup-modular
unzip /home/ops/core-backup-platform-2.0.zip -d /opt/core-backup-modular
chmod 700 /etc/core-backup-ops /etc/core-backup-modular
```

已有环境更新前确认没有上传/校验/网页任务运行；备份程序目录、配置和 service。不要在备份运行时重启平台服务，systemd可能终止其子进程。


### 4.5 首次中台配置（已有环境不要覆盖）

全新安装时，用样例初始化第一台185；已有生产配置则保留原文件：

```bash
test -e /etc/core-backup-ops/ops185.json || install -m 600 /opt/core-backup-modular/ops185.example.json /etc/core-backup-ops/ops185.json
test -e /etc/core-backup-ops/notify.json || install -m 600 /opt/core-backup-modular/notify.example.json /etc/core-backup-ops/notify.json
```

编辑notify.json：Enabled改为true，WebhookUrl填公司机器人地址。客户端包内notify.json默认也关闭，首次安装须分别填写。样例不会自带真实凭证。

先核对ops185.json的host、key、known_hosts、backup_dir和三个targets。挂载完成后执行：

```bash
python3 /opt/core-backup-modular/run.py --servers 185 --action check
python3 /opt/core-backup-modular/backup-all-smb.py --servers 185 --collect-only --verify-md5 off
```

其余五台按第7节register-client.py逐台登记，asset须与第3节各客户端配置完全相同；16用专用RSA密钥。没有首次成功源端标记时，先在该客户端生成，不要伪造DONE。

## 5. SMB 挂载与更换 NAS

最终路径统一是共享根目录，不加“核心资产备份”：

```text
\\10.10.11.243\资源备份\资产名\2026-11-19\运行号\
\\192.168.5.240\资源备份\资产名\2026-11-19\运行号\
\\10.10.10.254\资源备份\资产名\2026-11-19\运行号\
```

凭证文件用编辑器写入，不能用含密码的命令行：

```ini
username=填写账号
password=填写密码
# 如NAS确实需要域，再填写 domain=实际域
```

```bash
chmod 600 /root/.smb-nas243 /root/.smb-nas240 /root/.smb-share254
mkdir -p /mnt/core243 /mnt/core240 /mnt/core254
```

在 /etc/fstab 配置以下三行。先备份 fstab；已有同挂载点条目则修改，不要重复追加：

```fstab
//10.10.11.243/资源备份 /mnt/core243 cifs credentials=/root/.smb-nas243,vers=2.0,iocharset=utf8,file_mode=0600,dir_mode=0700,_netdev,nofail 0 0
//192.168.5.240/资源备份 /mnt/core240 cifs credentials=/root/.smb-nas240,vers=3.0,iocharset=utf8,file_mode=0600,dir_mode=0700,_netdev,nofail 0 0
//10.10.10.254/资源备份 /mnt/core254 cifs credentials=/root/.smb-share254,vers=3.0,sec=ntlmssp,iocharset=utf8,file_mode=0600,dir_mode=0700,_netdev,nofail 0 0
```

分别 mount /mnt/core243 等。nofail只影响启动，不保证失联SMB读写不阻塞。不要因挂载慢启用SMB1或关闭防火墙。

更换NAS地址/共享名必须同时修改：

1. NAS创建共享、备份账号与目录权限。
2. root凭证文件（如有变化）。
3. /etc/fstab 的 UNC；保持本地挂载点可减少改动。
4. 每台 opsNNN.json 的 targets[].source，必须与真实挂载共享精确一致。
5. 如挂载点也变了，同步 targets[].mount。
6. 无任务运行时正常 umount，再 mount；失败先查占用，不强制卸载正在写入的备份。
7. 网页检查通过，并在 Windows UNC 中查看实际文件，不只看 ops 的 /mnt。

更换共享不会自动迁移历史数据。本地历史 last-result 可能仍引用旧结果，执行新上传会复核实际目标文件。旧目标文件需按迁移计划保留，不能改凭据后立即删除旧盘。

如只更换某资产子目录，当前子目录由 asset 决定。asset同时用于客户端标记和中台归属验证，不能只改一端；建议保持资产标识稳定。当前不支持每目标独立子目录模板。

## 6. SSH、密码与凭证轮换

ops→客户端使用 SSH 私钥，不使用服务器密码做每日登录。修改 root/ops 登录密码通常不影响已有公钥认证。

```bash
mkdir -p /opt/core-backup-ops/ssh
chmod 700 /opt/core-backup-ops/ssh
ssh-keygen -t ed25519 -N '' -f /opt/core-backup-ops/ssh/id_ed25519
ssh-copy-id -i /opt/core-backup-ops/ssh/id_ed25519.pub -o UserKnownHostsFile=/opt/core-backup-ops/ssh/known_hosts root@新服务器IP
```

已存在密钥时不要重新生成覆盖。首次接受主机指纹前，在客户端控制台执行 ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub 对照；禁止 StrictHostKeyChecking=no。

旧16的sshd不支持Ed25519。使用其专用 id_rsa16，并仅针对该主机在 /root/.ssh/config 配置：

```sshconfig
Host 192.168.0.16
    IdentityFile /opt/core-backup-ops/ssh/id_rsa16
    IdentitiesOnly yes
    PubkeyAcceptedAlgorithms +ssh-rsa
```

这是旧协议兼容例外，不全局放开。源配置key也指向id_rsa16。后续系统维护时解决旧sshd，而不是在线备份中随意替换二进制。

密钥轮换：生成新文件→部署新公钥→显式-i新密钥严格模式验证→修改ops配置key→检查/分发通过→再撤销旧authorized_keys中的那一条公钥。保留回滚窗口，不删除其他运维人员密钥。

NAS密码轮换：停用调度并等任务结束→备份凭证文件→修改密码→正常重挂该目标→检查读写→恢复调度。密码不写进JSON、日志、crontab或聊天。

Web令牌轮换：空闲时停止core-backup-portal，备份admin.token，写入新随机令牌并chmod600，再启动。SSH隧道账号密码变化仅影响管理员建立隧道，不影响源端公钥备份。

## 7. 新增 GitLab 的中台操作

先完成第4节客户端安装、首次生成、公钥认证。

以下例子使用编号200；它必须唯一，host/IP不必等于编号。模板会继承185的三个目标与策略，请检查是否适合新机器：

```bash
python3 /opt/core-backup-modular/register-client.py \
  --id 200 --host 10.10.10.200 \
  --asset 'gitlab07_10.10.10.200_新增代码库' \
  --backup-dir /data/gitlab/backups

python3 /opt/core-backup-modular/run.py --servers 200 --action check
python3 /opt/core-backup-modular/run.py --servers 200 --action upload --verify-md5 off
```

新增JSON拒绝覆盖已有配置。按需修改user、key、minimum_free_gb、keep_days、cleanup_mode和targets。本版整批脚本、周校验会自动发现ops数字.json；无需修改Python中的固定六台列表。

若某资产只需两个目标，单任务run.py支持targets列表；现有backup-all-smb.py仍要求三个目标用于当前GitLab策略。不要把两端资产纳入该整批任务而期待自动放宽。Nexus已确定只需243/254，需其独立适配器。

网页配置在启动时加载；等网页任务结束后重启服务，新增卡片才出现。检查新NAS UNC内的资产/日期/运行目录、三个文件与pending.json。Webhook不能代替实际文件检查。

## 8. 自动调度、保留与校验

只选一个中台自动调度入口：推荐 cron，网页周期均关闭。网页手动检查/重试仍可用。页面和cron共用整批锁，冲突会跳过；手动命令优先使用backup-all-smb.py，避免绕开整批锁。

```cron
20 * * * * /usr/bin/python3 -u /opt/core-backup-modular/backup-all-smb.py --collect-only --verify-md5 off >> /var/log/core-backup-all-smb.log 2>&1
0 18 * * 6 /usr/bin/python3 -u /opt/core-backup-modular/verify-history.py >> /var/log/core-backup-history-md5.log 2>&1
```

这不是精确补偿调度：冲突会跳过，不自动补跑周任务，须按告警人工补跑。若周复核持续很久，小时上传会跳过，源端仍继续生成。NAS失联可能导致内核I/O等待，Python超时不等于保证立即打断内核等待。

SMB策略配置：

```json
{"keep_days":15,"cleanup_mode":"delete"}
```

keep_days指最近N个不同的成功日期；同日多个成功运行都保留，因此不是严格N个文件。不足N个日期不删除；日期有缺口向前补足。每端独立清理，只处理带本工具归属回执并与ops本地凭据一致的备份。未知目录、额外文件、异常大小阻断该端清理。

```bash
# 统一六台既有配置；新加机器要在自身JSON设置
python3 /opt/core-backup-modular/set-retention.py --days 15 --mode plan
# 核对CLEANUP_PLAN后启用实际删除
python3 /opt/core-backup-modular/set-retention.py --days 15 --mode delete
```

off模式清理依据存在/大小，不承诺内容完整；on模式完整MD5。两者都遵守cleanup_mode。删除是实际删除，审计记录不是回收站；误删恢复依赖NAS快照或其他副本，不能承诺完全可逆。

本机GitLab保留与SMB独立：backup_keep_time=259200是3天、1296000是15天。它按时间清理，不会确认三端上传成功，也不是“最近3份成功”。gitlab.rb修改通常需受控reconfigure，不能在业务机器盲目批量执行。本版不自动修改本机保留或删除本机归档。

周校验读取所有受管理历史文件，已存在MD5则与旧值比；pending则尝试源文件生成基准。源已删除而无旧MD5时报告unverifiable，不伪造通过；校验报告不会将pending回执自动升级。需要长期可核对基准时，应在源备份完成时保存可信MD5，这是后续优化项。

## 9. 告警配置与排查

notify.json沿用原notify.py字段，示例见包中example文件。Webhook密钥是凭证，不能提交Git或放到公开页面。更换URL前备份、编辑文件并chmod600；源端通知和ops通知是两份配置，要分别更新。

告警包括：环境检查、源端开始/结束、收集与目标结果、清理结果、历史复核异常和总结。通知失败不代表数据复制失败；日志有NOTIFY_FAILED。中台通知投递记录在 /var/lib/core-backup-ops/modular-notify/events.jsonl，**没有承诺永久重试队列**。

当前无完整“某天未触发即报警”的独立监控；有执行才有结果。cron未运行、主机断电或Webhook不可达时，不能靠该任务自报一切正常。后续应接公司监控系统做最后成功时间阈值监测。

## 10. 网页控制台升级、访问与验收

本页2.0增加：全部检查、全部收集/重试、每源SSH/完成标记/备份大小/磁盘、每端读写/剩余总容量、最近批次/三端结果/校验状态、收集分发耗时和日志。

“一键检查”后台串行排队，可能数分钟；不是瞬时探测。NAS采样数据重复显示在相关资产卡片；没有最近检查报告的显示未采集，不显示绿色通过。源端磁盘来自df，NAS容量来自挂载后statvfs，配额/共享卷会影响数值，以实际NAS管理端为准。

升级时先确认网页/cron/周任务均空闲，然后：

```bash
cp -a /opt/core-backup-modular /opt/core-backup-modular.before-portal2
cp -a /etc/systemd/system/core-backup-portal.service /root/core-backup-portal.service.before-portal2
unzip -o /home/ops/core-backup-platform-2.0.zip -d /opt/core-backup-modular
install -m 644 /opt/core-backup-modular/core-backup-portal.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now core-backup-portal
systemctl restart core-backup-portal
systemctl status core-backup-portal --no-pager
```

首次安装没有旧service时，备份那条cp会报不存在，可跳过。旧令牌及schedules.json沿用。周期调度务必保持关闭，沿用cron。

## 11. 其他组件如何统一纳管

共同抽象是“源端生成器 + 完成清单 + 收集适配器 + 分发/校验/保留 + 调度结果”。统一结果应有asset、os、component、run、开始结束、阶段用时、文件列表、每端状态和校验级别。只有生成器退出成功并验证清单后才发布完成标记。

当前GitLab清单固定三文件、归档名与.core-complete协议；需要先扩展验证器和收集适配器，不能用改后缀的方式让别的组件混过去。Windows旧PS2机器也不能假设有OpenSSH或现代JSON命令。

|组件|源端责任|纳管前必须验证|
|---|---|---|
|Oracle|Windows本地expdp，或Oracle服务账号可写UNC的直写；rc=0后清单|SID/home/directory真实对应、退出码和ORA错误、空间、服务身份UNC写入、导入测试。41有205错误，禁止成功标记|
|SVN|svnadmin hotcopy，每仓库成功后汇总清单，连同授权配置|SMB可写、12仓库齐全、UUID/版本、svnadmin verify及独立恢复权限；不得停服务或删除源库|
|Nexus2|确认work目录和外部仓库路径，制定一致性快照/受控停写方案|真实10.10.10.51身份、配置及仓库一致性、恢复读制品验证；只需243/254按资产targets配置|
|Harbor|记录原读写状态→暂停push/delete/GC并等后台写入结束→DB导出+registry/config/secrets→恢复原状态|不能只打包活动PGDATA；异常必须恢复原只读设置；周日03:00保留3份成功；额外postgres容器是另一资产|

Windows任务需独立执行身份凭证，交互net use会话不自动继承给计划任务。OracleService为LocalSystem时直写NAS需要真实Oracle进程UTL_FILE探针，而不是管理员资源管理器能写就算通过。

在适配器完成前：各组件保留独立本机计划任务和日志，使用相同Webhook消息字段，登记人工验收结果。当前网页仅展示GitLab，不能承诺一键调度这些未接入组件。后续扩展应先用一个小样本资产端到端验收，再批量纳入。

## 12. 故障定位速查

|现象|先查什么|
|---|---|
|Already running|源端已有备份，不杀进程/删锁；等SOURCE_COMPLETE后collect-only|
|Another batch running|互斥正常；区分周校验或上传，不重复启动|
|NAS目录空但last结果成功|核对共享根、UNC、mount/source和日期run；旧记录非实时证明|
|SMB13/STATUS_LOGON_FAILURE|凭证和共享权限，不能用chmod修远端登录|
|SMB112/445timeout|路由/IP冲突/防火墙/服务，先TCP而非降级SMB|
|df -h卡住|先df -lh看本机，别反复访问故障挂载；保持运行任务现场|
|No space left但df剩余|检查真实backup_path所在卷与df -i|
|主机key mismatch|在控制台核对指纹，禁止直接删除known_hosts绕过|
|NOTIFY_FAILED|DNS、出站443、TLS、机器人配置；不等同备份失败|
|MD5 unavailable|pending历史源文件已删且无可信基准，不是校验通过|
